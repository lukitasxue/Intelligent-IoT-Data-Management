# Backend Analytics Integration Handover

**Status:** Week 7 – In Progress

## 1. Purpose

This document provides the current Backend handover information for the Analytics Integration work. It brings together the Backend requirements, Analytics input and output contracts, Models and Correlation integration details, validation requirements, testing evidence, and remaining integration tasks.

The purpose is to ensure that the Backend team has a clear understanding of how it should communicate with Analytics Integration and what information and response structure should be expected.

## 2. Backend Integration Status

The Backend integration with Analytics Intelligence (AIntl) has now been implemented and merged through **PR #16 – feat(backend): integrate analyse API with Analytics Intelligence**.

Previously, the Backend `POST /api/analyse` endpoint contained placeholder behaviour. The updated implementation now performs a real HTTP request to the Analytics Integration service through:

```
POST /analytics/analyze
```

The Backend receives the Analytics response and returns the shared Draft V0.1 Analytics response to the Frontend.

The implemented integration also includes configurable AIntl settings:

- `ANALYTICS_SERVICE_URL`
- `ANALYTICS_TIMEOUT_MS`

Canonical ThingSpeak field mappings have also been added, including the mapping for channel `1350261`.

The Backend now handles several upstream situations, including validation errors, unavailable AIntl services, request timeouts, upstream failures, and invalid AIntl responses.

The PR also added Backend integration tests. The reported validation shows that `npm test` passes, and a live Backend → AIntl smoke test returned HTTP 200, processed 120 readings, and returned real Analytics alerts.

## 3. Backend Endpoint Relationship

The Backend's existing public analysis endpoint is:

```
POST /api/analyse
```

This is the endpoint used by the Frontend to request analysis through the Backend.

When analysis is required, the Backend communicates with Analytics Integration through:

```
POST /analytics/analyze
```

The internal Correlation endpoint:

```
POST /detect-correlation-alert
```

should **not** be treated as the Backend-facing Analytics endpoint. It belongs to the internal Correlation component.

This distinction is important because Backend should communicate with the Analytics Integration boundary rather than directly depending on the internal implementation of the Correlation service.

## 4. Backend Input Requirements

The Backend is expected to provide normalised sensor data to Analytics Integration.

The input needs to provide the sensor identifier, analysis time window, and sensor readings. Each reading requires a timestamp and numeric value. Optional parameters can be provided when analysis configuration is required.

The currently documented structure includes:

- `sensor_id`
- `time_window`
  - `start_time`
  - `end_time`
- `data_points`
  - `timestamp`
  - `value`
- Optional parameters
  - `detectors`
  - `sensitivity`

**Example:**

```json
{
  "sensor_id": "sensor_1350261",
  "time_window": {
    "start_time": "2026-08-24T10:00:00Z",
    "end_time": "2026-08-24T10:30:00Z"
  },
  "data_points": [
    {
      "timestamp": "2026-08-24T10:00:00Z",
      "value": 24.5
    },
    {
      "timestamp": "2026-08-24T10:01:00Z",
      "value": 25.1
    }
  ],
  "parameters": {
    "detectors": [
      "IsolationForestDetector"
    ],
    "sensitivity": 0.8
  }
}
```

The Backend integration also includes canonical ThingSpeak field mappings and timestamp handling.

The final Backend input specification is still being aligned with Adharsh's AI-030 documentation, so this section should be reviewed once that work is corrected and approved.

## 5. Models Integration

The Models Output Adapter converts the output generated by the Models component into the common Draft V0.1 Analytics alert format.

The adapter is responsible for mapping model-specific fields into the shared structure and producing the required alert information. The supported Models alert type is:

```
POINTWISE_ANOMALY
```

The Models adapter was tested successfully with:

- **17/17 tests passed**

A runnable adapter test also generated two `POINTWISE_ANOMALY` alerts. The field mapping between the Models output and the Draft V0.1 structure was also verified.

This means the Models output is ready to be consumed by the shared Analytics response process.

## 6. Correlation Integration

The Correlation component provides correlation-change results that need to be converted into the same Draft V0.1 structure used by Models.

The expected Correlation alert type is:

```
CORRELATION_CHANGE
```

The Correlation Output Adapter is responsible for converting Correlation-specific results into the common Analytics alert structure.

The main remaining work for this area is to complete the final verification that Correlation output is correctly transformed and accepted by the shared validation process.

## 7. Shared Analytics Response

The Models and Correlation adapters produce standardised alerts which are combined into the shared Draft V0.1 Analytics response.

The Shared Envelope Builder has already been implemented and reviewed. It provides a consistent response structure containing fields such as:

- `status`
- `generated_at`
- `alerts`
- `summary`
- `errors`

Testing of the Envelope Builder covers Models-only results, Correlation-only results, combined results, no-alert responses, UTC `generated_at`, JSON serialisation, error status, and invalid processed items.

This allows Backend to consume a consistent response without needing to understand the different internal formats produced by Models and Correlation.

## 8. Shared Validator

The Shared Validator is used to validate the final Draft V0.1 Analytics response before it is returned to Backend.

The validator checks areas such as:

- Required fields
- Data types
- Timestamp format
- Severity values
- Alert structure
- Missing fields
- Invalid fields

Vrushank's contract regression test PR has now been merged.

The reported test results were:

- **14** new contract regression tests
- **23** existing validator tests
- **37** tests passed in total

The regression coverage protects the contract against changes to required fields, data types, timestamps, severity and invalid input.

Additional confirmation is still useful for the `CORRELATION_CHANGE` alert case and the current `severity: null` behaviour.

## 9. No-Alert Behaviour

A successful analysis does not necessarily mean that alerts will be generated.

When no anomaly or correlation change is detected, the response should still be treated as a successful Analytics operation. The `alerts` field should contain an empty array rather than the request being treated as a failure.

**Example:**

```json
{
  "status": "success",
  "generated_at": "2026-08-24T10:30:00Z",
  "alerts": [],
  "summary": {},
  "errors": []
}
```

Backend should therefore distinguish between a valid analysis that produced no alerts and an actual Analytics service failure.

## 10. Failure and Partial-Success Handling

The Analytics Integration team has been working on consistent failure-handling behaviour across Models and Correlation.

The main cases being covered are:

- Models failure
- Correlation failure
- Both services failing
- Partial success
- Empty output
- Malformed output
- Invalid timestamps
- Missing required fields
- Analytics service unavailable
- Runtime errors

The expected behaviour is that failures are represented through the agreed shared response contract rather than each component returning a different structure.

For example, if one Analytics component succeeds while another fails, the response should be able to represent the partial-success situation. If both services fail, the response should represent an Analytics failure.

The final failure-handling behaviour still requires verification against the implemented adapters, envelope builder and validator.

## 11. Backend Error Handling

PR #16 has added Backend-side handling for AIntl communication failures.

The implemented handling includes:

- Validation errors
- AIntl unavailable
- Request timeout
- Upstream failure
- Invalid AIntl response

This provides a clear failure boundary between Backend and Analytics Integration.

Backend does not need to directly manage the internal failure behaviour of Models or Correlation. Those internal failures should be handled by Analytics Integration and represented through the agreed Analytics response contract.

## 12. Alert Persistence

Alert persistence and retrieval are currently not included in the Backend → AIntl integration.

PR #16 specifically identifies this as outside the current implementation because the Backend alert persistence layer is not currently available.

Therefore, Analytics alert generation and Backend communication are implemented, but persistent storage and later retrieval of generated alerts remain a separate requirement.
